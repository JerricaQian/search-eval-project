## 三档解释与证据展示契约

问题解释统一契约（必填）通用条款见 [[组件卡片评测通用契约]]（`phase3-card_or_component-eval/组件卡片评测通用契约.md`），本 Skill 不重复列出。

### 组件色彩问题文案口径（强制，技能专属，不套用通用简洁问题卡两句式写法）

- 本 Skill 的问题颗粒度是**组件**，`elementId` 仅用于红框定位，不能把单个标签的原文、坐标当作组件色彩结论的 `observableFact`。每条 issue 必须从该组件同一条 `assessmentRows` 读取 `colorFamilies` 与 `colorFamilyCount`，并使用中文色系名称；禁止输出 `yellow`、`cyan` 等英文枚举。
- `finding.observableFact` 固定表达为：`<组件ID> 的<可见区域>测得<中文色系1>、<中文色系2>……共 N 个有效 UI 有彩色系`。`N` 必须等于该组件 `assessmentRows.colorFamilyCount`，色系列表必须与 `colorFamilies` 一致。
- `finding.ruleOrThreshold` 固定完整表达为：`组件有效 UI 有彩色系≤3种为优秀，4–5种为达标，≥6种为不达标`。不得只写“有彩色系4至5为达标”或“超过5个为不达标”等截断规则。
- `finding.verdictReason` 固定表达为：`N 个有效 UI 有彩色系，处于<优秀/达标/不达标>区间；因此评级为<评级>`。不得使用“当前计数命中达标区间”“触发色彩过多阈值”等没有回指具体计数和评级的泛化句。
- `finding.userImpact` 必须落到该组件的标题、价格、履约、权益或标签等实际竞争对象；不得用“保留当前信息可用性”等与色彩事实无关的套话。
- 问题卡简洁展示示例：`C3 的履约、标签、价格与保障区域测得黄、橙、蓝、青、红、绿共 6 个有效 UI 有彩色系，评级为不达标。履约、促销和保障色同时抢占视觉注意力，分散商品标题与价格的焦点。`

- 每个 Tab 的优秀、达标、不达标均须输出非空 `reason`（评级与可见事实）、`details.criterion`（命中规则/阈值）、`details.summary`（范围及正向/负向证据）；优秀不得只写"无问题"。
- `assessmentRows` 覆盖模式（技能专属）：每个 Tab 必须输出覆盖全部评估组件的 `assessmentRows`；每行除既定字段外必须写出该组件的可见事实、命中规则和评级解释。
- `details.evidenceMode`：可定位问题为 `annotated-region`；兼有局部与整体/关系结论为 `hybrid`；无唯一坐标的整体/关系结论为 `original-page`，且 `details.screenshot` 必须指向存在的原图。
- 优秀仅在评测详情保留 `reason`、`criterion` 和 `summary` 解释，不得进入发现问题/治理项；达标、不达标才进入待优化项。

## 工具定位

本 Skill 用于评测搜索结果页或信息页截图中的**色彩运用逻辑性**，即每个UI组件是否将有彩色控制在合理数量内、色彩运用是否克制统一。AI 通过 Python 脚本对截图进行像素级分析：先排除照片、营销素材、金刚 icon 等非 UI 色彩像素，再将剩余像素按 36 色 HSV 标准分类并合并同色系，最终统计每个组件的有彩色系数量，按标准给出评级结论。最终按**搜索词 × 组件**颗粒度输出评测结论。

**与同系列 Skill 的边界：**

- 本 Skill 关注"UI 色彩数量是否可控、运用是否有逻辑"（色彩复杂度问题）。
- `eval-5-info-hierarchy` 关注"商卡组件的信息层级是否复杂"（信息复杂度问题）。
- `eval-4-element-complexity` 关注"标签/icon 样式是否过多"（静态元素复杂度问题）。
- 三者互不重叠：同一组件可能同时被三个 Skill 分别评测，互不影响。

## 核心概念

### 36 色 HSV 分类标准

"36 色标准"是本评测体系的名称。实际分类规则为：所有像素先从 RGB 转为 HSV（H: 0–360°, S: 0–100, V: 0–100），按饱和度 S 分为无彩色和有彩色两大类：

**无彩色判定（S < 12）：** 饱和度低于 12 的像素视为无彩色，按明度分 5 级：白色（V > 90）、浅灰（65 < V ≤ 90）、中灰（40 < V ≤ 65）、深灰（15 < V ≤ 40）、黑色（V ≤ 15）。无彩色统一归入 `achromatic` 色系，不参与有彩色系计数。

**有彩色判定（S ≥ 12）：** 按色相 H 值分为 9 个色相区间（其中红色跨越 0°/360° 分界点，分为 0–15° 和 330–360° 两段但归入同一色系），每个区间按明度分深浅两档（V > 60 为浅色，V ≤ 60 为深色），共 18 个有彩色格。色相区间如下：

| 色相区间 | H 范围 | 对应色系 |
|---------|--------|---------|
| 红 | 0–15° / 330–360° | red-family |
| 橙 | 15–45° | orange-family |
| 黄 | 45–68° | yellow-family |
| 黄绿 | 68–85° | yellow-green-family |
| 绿 | 85–150° | green-family |
| 青 | 150–195° | cyan-family |
| 蓝 | 195–250° | blue-family |
| 紫 | 250–290° | purple-family |
| 品红 | 290–330° | magenta-family |

### 同色系合并

同一色相区间内的深色和浅色合并为同一个"色系"（family）。例如浅红色（red-light）和深红色（red-dark）同属 `red-family`，只计为 1 个色系。最终统计的"有彩色系数"即合并后的色系去重数量。

### 占比过滤

单个色格的像素占比低于 1% 的不计入统计（避免渲染锯齿、亚像素混色等噪声干扰评级）。

### 排除像素

以下像素不参与色彩统计：

- **白色背景**：RGB 三通道均 ≥ 247 的像素，视为页面背景。
- **照片像素**：通过照片区域检测算法识别出的商家头图、商品图、菜品图等实拍/设计素材的像素。
- **金刚区 icon**：金刚位入口图标属于平台运营素材，色彩由运营配置而非 UI 设计决定，应整体排除。
- **营销素材**：Banner、腰封等营销推广区域的像素。

**不排除的像素：** 照片区域上叠加的 UI 元素（角标、价格标签、活动标签等）应保留参与统计，因为这些元素的色彩由 UI 设计决定。

## 评估标准

对**每个组件**独立评估：

| 评级 | 条件 | 含义 |
|------|------|------|
| 🟢 优秀 | 有彩色系数 ≤ 3 | 色彩克制统一 |
| 🟡 达标（良好） | 有彩色系数 = 4 或 5 | 色彩复杂度适中 |
| 🔴 不达标（需优化） | 有彩色系数 ≥ 6 | 色彩过于复杂 |

> **评级说明：** "有彩色系数"仅统计有彩色（S ≥ 12）的色系数量，无彩色（黑/白/灰）不参与计数。同一色系内不论包含几种深浅变体，始终只计 1 个色系。

## 执行步骤

### Step 1：接收截图并确认评测范围

1. 用户提供页面截图（单张或多张）。使用图片读取工具加载所有截图，确认图片尺寸和内容。
2. 识别搜索词（顶部搜索栏文字）；若为非搜索场景（如详情页、列表页），识别页面所属场景名称代替搜索词。
3. 识别当前 Tab/频道（全部、外卖、团购等），若页面无 Tab 概念可省略。
4. 判断截图类型：**整页截图**还是**单组件截图**。判断依据：若截图包含搜索栏/Tab栏/筛选栏等页面级 UI 元素且纵向涵盖多个组件区域，为整页截图；若截图仅包含一个商卡或组件、没有页面级导航元素、组件内容几乎占满整张图片（无明显的白色背景间隔分隔多个组件），为单组件截图。两种类型的照片检测策略不同，详见 Step 3。

### Step 2：识别页面中的组件并确定 y 坐标范围

从截图顶部到底部，按视觉顺序识别页面中的所有组件区域。每个组件需记录 `y_range`（组件在截图中的纵向像素范围），横向默认取整个截图宽度。

典型的组件类型包括：

- **搜索栏**：页面顶部的搜索输入区域。
- **Tab 导航栏**：全部/外卖/团购等频道切换区域。
- **筛选栏**：排序、筛选按钮所在条。
- **快筛区/图筛区**：图标式快速筛选入口。
- **金刚区**：平台运营的品类入口 icon 区域（**标记为排除，不参与色彩评测**）。
- **商卡**：搜索结果中的商品/商家卡片，每张为独立组件。
- **营销素材**（Banner / 腰封）：**标记为排除，不参与色彩评测**。

为每个组件编号、命名，记录其 `y_range`。若为单组件截图，则只有一个组件，`y_range` 覆盖整张图片。

### Step 3：编写 Python 脚本 — 照片区域检测

根据截图类型选择合适的照片检测策略：

**策略 A：整页截图 — 轮廓分类合并法**

适用于包含多个组件的完整搜索结果页截图（有白色背景间隔分隔各组件）。

1. **检测内容轮廓**：将图片中 RGB 三通道均 ≥ 247 的像素标记为白色背景，取反得到内容 mask，做 3×3 开运算去噪，用 `findContours` 提取所有内容区域的外轮廓。过滤面积 < 30 的微小轮廓。
2. **逐轮廓分类（photo / ui）**：对每个轮廓的 bounding rect，先用快速规则排除明显的 UI 区域（面积 < 300、高度 < 15、y < 100 状态栏区域、宽高比 > 3.5 的窄条、色相标准差 < 10 且面积 < 20000 的纯色标签），再综合面积、色相分散度（hue 直方图 active bins 数，以 18 bins 统计占比 > 2% 的 bin 数）、RGB 标准差、有彩像素占比、宽高比等特征匹配 photo 规则。典型的 photo 判定条件包括：面积 ≥ 3000 且 active bins ≥ 3 且 RGB std ≥ 25；或面积 ≥ 1500 且 active bins ≥ 5 且 RGB std ≥ 35；或 icon 尺寸范围（30–160px）内正方形区域且有彩占比 ≥ 0.3 且面积 ≥ 2000。不满足任何 photo 条件的分类为 `ui`。
3. **合并邻近 photo 区域**：将距离相近的 photo bounding rect 合并（水平间距 ≤ 20px 或垂直间距 ≤ 15px 且存在交叠），得到合并后的 photo bounding box 列表。
4. **生成精确 photo mask**：用原始 photo 轮廓精确填充 mask（`drawContours` fill），不做额外膨胀，避免误覆盖轮廓边缘的 UI 元素。

**策略 B：单组件截图 — 网格评分 + 最大连通域法**

适用于单张商卡/组件的裁剪截图（无白色背景分隔，组件内容占满整张图片）。

1. **网格划分**：将截图按 40×40 像素网格划分。
2. **网格评分**：对每个网格计算三项特征得分并加权求和：Canny 边缘密度（权重 0.4，反映纹理丰富度）、RGB 通道标准差均值（权重 0.35，反映颜色变化丰富度）、色相 bin 数（将有彩像素 H 值分 12 bins，统计有效 bin 数，权重 0.25，反映色相分散度）。总分归一化到 0–1。
3. **二值化 + 最大连通域**：对评分矩阵做 Otsu 阈值二值化，提取所有连通域，仅保留面积最大的一个连通域作为照片区域。此策略的核心假设是：单组件截图中照片（商品图/头图）通常是最大的一块连续高纹理区域，而 UI 标签虽然可能评分较高但面积远小于照片。
4. **二次验证**：对最大连通域区域回验其平均 RGB 标准差和色相 bin 数，确认确实具有照片特征（RGB std ≥ 20 且 hue bins ≥ 2），否则不标记为照片。
5. **生成 photo mask**：将最大连通域对应的网格区域映射回像素级 mask。

**照片区域上的 UI 叠加元素（角标）保留：**

无论使用哪种策略，在得到 photo mask 后，需在 photo bounding box 范围内检测叠加的 UI 元素（角标、价格标签等），将这些像素从排除 mask 中移除（即保留参与色彩统计）。角标检测条件：在 photo 区域内找高饱和度（S > 100）且高明度（V > 70）的连通像素块，面积不超过 photo bbox 面积的 15%，且色相标准差 < 15（纯色特征）。同时保留角标内的文字像素（灰度 > 220 的白色文字或 < 60 的黑色文字）。

### Step 4：编写 Python 脚本 — 色彩分析

1. **构建排除 mask**：`exclude_mask = photo_mask AND NOT overlay_mask`（照片像素排除，角标像素保留）。
2. **构建白色背景 mask**：RGB 三通道均 ≥ 247。
3. **提取有效像素**：组件 y_range 内，既非排除像素、也非白色背景的像素为有效像素。
4. **向量化 HSV 计算**：将有效像素 RGB 转为 HSV（H: 0–360°, S: 0–100, V: 0–100）。若有效像素超过 300,000，随机采样 300,000 个（种子固定为 42，保证可复现）。
5. **36 色分类**：按核心概念中的分类标准，将每个像素归入 36 格之一。
6. **过滤 + 合并**：剔除占比 < 1% 的色格，将同色相区间的深/浅归入同一色系，统计有彩色系数量。
7. **评级**：按评估标准判定。

### Step 5：运行脚本并生成调试图

1. 运行 Python 脚本，对每张截图执行照片检测 + 色彩分析。
2. 生成调试图（debug image）：在原图上用红色半透明覆盖被排除的 photo 像素，绿色高亮标记被保留的角标像素，蓝色细框标记 photo bounding box。
3. 检查调试图：确认照片区域是否正确标记（不应误覆盖 UI 元素如标签、文字、按钮），角标是否正确保留。若发现误判，回到 Step 3 调整检测参数后重新运行。

### Step 6：输出结果

**6a. 组件级评测明细表：**

| 搜索词 | Tab/场景 | 组件 | 有效像素 | photo排除像素 | 有彩色系数 | 主要色系 | 评级 |
|--------|----------|------|---------|-------------|-----------|---------|:----:|
| 搜索词 | Tab名 | 组件名 | N | N | 有彩色系数 | 色系列表 | 🟢/🟡/🔴 |

**6b. 评级分布汇总（按搜索词 × Tab 维度）：**

| 搜索词 | Tab/场景 | 🟢 优秀 | 🟡 达标 | 🔴 不达标 | 总组件数 |
|--------|----------|:------:|:------:|:--------:|:-------:|
| 搜索词 | Tab名 | N | N | N | N |

**6c. 色系分布明细（按需展示）：**

对评级为 🟡 或 🔴 的组件，展开列出其所有有彩色系及各色系占比，帮助定位哪些色彩可以合并或去除：

| 组件 | 色系 | 占比 | 包含色格 |
|------|------|------|---------|
| 组件名 | red-family | X.X% | 浅红色 X.X% + 深红色 X.X% |

**6d. 总结说明：**

在表格下方附一段文字总结，包含：不达标组件的具体问题（如"使用了 6 个以上色系，建议合并相近色系"）、整体色彩运用趋势、以及优化建议（哪些色系可以合并、哪些低占比色彩可以去除）。

## 分支处理

| 场景 | 处理方式 |
|------|---------|
| 单张整页截图、单个 Tab | 直接按 Step 2–6 分析，使用策略 A 检测照片 |
| 多张截图、同一 Tab 不同屏 | 分屏分析后合并为一份完整报告，组件按出现顺序统一编号 |
| 多张截图、不同 Tab | 每个 Tab 独立分析，分别输出表格和评测结论 |
| 多张截图、不同搜索词 | 每个搜索词独立评测，最终汇总所有搜索词的评级分布 |
| 单组件截图（一张商卡裁剪图） | 使用策略 B 检测照片，只有一个组件，y_range 覆盖全图 |
| 组件内无有效像素（全部被排除或全白） | 评级标记为 🟢 优秀，备注"无有效像素" |
| 组件中无照片区域（纯 UI 组件如搜索栏、筛选栏） | 跳过照片检测，直接对全部非白色像素做色彩分析 |
| 深色/非白色背景的页面 | RGB ≥ 247 的白色背景阈值不适用，需改用其他背景检测方式（如取四角像素颜色作为背景色），或与用户确认排除策略 |
| 金刚区组件 | 整体标记为"排除（运营素材）"，不参与色彩评测，不出现在评级统计中 |
| Banner / 腰封等营销素材 | 同金刚区，整体排除 |
| 调试图显示 UI 元素被误标为 photo | 调整照片检测参数（如提高面积阈值、收紧色相分散度条件），重新运行 |
| 调试图显示照片未被检测到 | 放宽检测条件（如降低 RGB 标准差阈值、降低面积门槛），重新运行 |
| 组件底部被截断 | 仅分析可见部分，组件名后注明"（部分截断）" |
| 用户要求与之前分析合并 | 回溯之前的分析结果，按多屏合并格式输出完整报告 |
| 同一组件横跨两屏截图 | 以信息更完整的一屏为准，只分析一次 |
| 单张截图内组件数量过多（10+ 商卡） | 仍逐一分析不做抽样，可在明细表中用简写编号控制表格长度 |

## Gotchas

- **照片像素必须排除，否则色系数虚高**：商家头图、菜品图等实拍照片天然包含大量色相，如果不排除将导致几乎所有商卡都被判为不达标。照片排除是整个评测的前提——跳过这一步得到的结果没有参考价值。
- **角标必须保留，否则遗漏 UI 色彩**：照片上叠加的角标（如"闪购""满减"标签）属于 UI 设计色彩，其颜色决定由设计师掌控，不应随照片一起排除。漏掉角标会低估组件的色系数。
- **整页截图和单组件截图的照片检测策略不同**：整页截图有白色背景分隔各组件，可以用轮廓法区分 photo 和 UI；单组件截图没有白色背景间隔，轮廓法会把整个组件识别为一个大区域，必须改用网格+最大连通域法。使用错误的策略会导致检测失败。
- **photo mask 不要膨胀**：精确填充原始轮廓即可。膨胀（dilate）会扩大 mask 边界，误覆盖照片边缘紧邻的 UI 元素（如紧贴头图边缘的标签），导致这些 UI 色彩被排除而漏统计。
- **无彩色不参与色系计数**：黑/白/灰无论出现多少种，统一归为 achromatic 且不计入有彩色系数。评级只看有彩色系的数量——一个组件即使同时用了白色背景、黑色文字、3 种灰色分隔线，只要有彩色系 ≤ 3 就是优秀。
- **同色系深浅合并**：浅红和深红是同一个色系，不要重复计数。评测的是"用了多少种色相方向"，而不是"用了多少种具体颜色"。
- **1% 占比过滤防止噪声**：渲染抗锯齿、图片压缩伪影等会产生微量杂色像素，不过滤会虚增色系数。但阈值不应设太高（如 5%），否则会漏掉有意使用但面积不大的强调色。
- **采样要固定随机种子**：像素数过多时需采样，必须固定种子（42），保证同一张图多次分析结果一致，否则评级结果不可复现。
- **金刚区和营销素材是排除整个组件，不是排除像素**：它们不进入 Step 4 的色彩分析流程，也不出现在评级结果表中。与"排除照片像素"（照片像素排除但组件仍参与评测）是两个不同层次的排除。
- **调试图是必要的质量保证手段**：每次分析都必须生成调试图并检查，尤其是首次分析新的页面类型时。不看调试图直接输出结果，无法发现照片检测的误判，结果不可信。
- **JSON 输出注意 numpy 类型转换**：脚本中使用 numpy 计算得到的整数类型（如 `np.int64`）不能直接 JSON 序列化，输出前需转换为 Python 原生 `int()`，否则运行时报错。
- **策略选择不能靠猜测**：必须在 Step 1 明确判断截图类型后再选策略。如果用整页策略处理单组件截图，轮廓法会将整个组件识别为一个巨大 photo 区域（因为没有白色背景分隔），导致所有像素被排除、分析结果为空。
